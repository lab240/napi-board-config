## Архитектура

Python 3.9+, PyYAML, curses; без микросервисов, отдельной БД и web-зависимостей.

- `napi_config/core/`: модели, EEPROM codec/CRC, MAC, serial/date,
  конфигурация/валидация, профили, расчёт boot-строк и общий `BoardService`.
- `napi_config/hardware/`: Linux EEPROM, sysfs/Device Tree, boot-файлы,
  стандартные overlay-каталоги, backups/read-back/reboot.
- `napi_config/storage/`: YAML/JSON и источник профилей.
- `napi_config/tui/app.py`: curses, ввод, представление, подтверждения.
- `napi_config/cli/app.py`: argparse, JSON/stdout/stderr и вызовы общего сервиса.
- `napi_config/bootstrap.py`: сборка адаптеров и сервиса.
- `napi-config`: основной запуск; `napi-board-config.py`: совместимый старый запуск.
- `boards.yaml`: reusable-профили; `platforms.yaml`: mappings/ID/conflicts.
- `tests/`: unittest; `ARCHITECTURE.md`: границы модулей.

TUI/CLI не реализуют аппаратную или бизнес-логику. Будущий REST/Web UI должен
вызывать тот же Core. Чтение v2 сохраняется; новые экземпляры используют v3.
Serial/date/MAC — данные экземпляра, не reusable-профиля; применение профиля их сохраняет.

## Согласованное поведение v18

- I2C1 — независимый интерфейс: можно включить без RTC и EEPROM.
  Defaults не включают шину принудительно. RTC требует I2C1 и при включении
  включает её; выключение шины при активном RTC отклоняется.
- Наличие I2C1 не означает наличие EEPROM. Автоматически EEPROM overlay не добавлять.
- Доступная EEPROM используется без требования отдельного overlay-файла:
  устройство может быть объявлено в основном DTB или через user overlay.
- Если EEPROM недоступна, предложить выбрать существующий **стандартный**
  `.dtbo` с EEPROM/24xx в имени. Имя — только признак кандидата, не проверка
  совместимости. Пользователь проверяет модель, шину и адрес.
- TUI: `Add EEPROM overlay and reboot` → выбор → CURRENT/PROPOSED → точное
  `yes` → backup/write/read-back → reboot. Просмотр и отмена ничего не записывают.
  Если устройство уже доступно, показать, что дополнительный overlay не нужен.
- Если стандартного кандидата нет: объяснить, что подходящий overlay можно
  установить и настроить вручную через `user_overlays`. Ничего не скачивать.
- **Не сканировать пользовательские overlay-каталоги, не менять их файлы
  и строку `user_overlays`.** Имена там могут быть произвольными.
- Недоступные операции EEPROM остаются видимыми как `disabled` с причиной.
  Отсутствие sysfs-узла означает «недоступна / не настроена», а не доказанное
  отсутствие EEPROM. I2C-адрес сам по себе не подтверждает тип устройства.
- `armbianEnv.txt`/`uEnv.txt` определяется автоматически; если есть оба —
  по deployed `boot.scr` (fallback `boot.cmd`), неоднозначность блокирует запись.
- Runtime `overlay_prefix` читать из env, не навязывать из YAML. С префиксом
  имена короткие, без него полные, без `.dtbo`. Префикс сохраняется.
- `View and write overlay string`: обе строки CURRENT/PROPOSED;
  предупреждения отдельно выше, не как часть предлагаемого файла.
  Недостающий стандартный overlay — предупреждение, поскольку его аппаратуру
  может обеспечивать произвольный user overlay. Обычная запись не перезагружает.
- Уже явно настроенный стандартный EEPROM overlay сохраняется обычным
  boot-plan, пока I2C1 включён. Специальное включение сохраняет остальные overlays.
- При старте TUI валидная EEPROM загружается автоматически; иначе defaults
  с причиной ошибки. MAC generation и загрузка профиля требуют подтверждения.

Новые CLI:

```bash
./napi-config eeprom overlays --json
./napi-config eeprom enable --overlay NAME --yes
```

NAME брать из `candidates[].name` первой команды. Дополнительный `--reboot`
явно разрешает reboot. Поддержаны `--platform`, `--boot-dir`, `--eeprom`.
Также доступны `eeprom show/write`, `mac generate`, `board info`, `overlay list`,
`boot show/preview/write`, `hardware detect`, `tui`, `--version`.

## Последнее изменение: v19, стабильные MAC из OTP

- v19 загружена в `/root/v19` на `root@192.168.30.53`, v18/v17 сохранены.
  Запуск: `cd /root/v19 && ./napi-config tui`.
- `core/mac.py`: namespace `b"NAPI-MAC-v1\x00"`, SHA256 от namespace + 5 бинарных
  байт OTP; первые пять байт digest, младшие три бита пятого обнулены;
  MAC = `02` + основа, младшие три бита последнего октета = slot 0..7.
  Никаких random/serial/time/UUID/hostname/current-MAC fallback.
- `hardware/otp.py`: `/sys/bus/nvmem/devices/rockchip-otp0/nvmem`, offset 20,
  length 5, read-only open, exclusive advisory `fcntl.flock` с таймаутом 2 секунды,
  seek/read/unlock. Ошибки открытия, lock, seek/read, короткий ID и нули/FF
  завершают генерацию: `MAC generation failed: invalid or unavailable RK3308 OTP ID`.
  Offset 8 (RKY32003) не использовать.
- `MacSlot`: MAC1 Native Ethernet, MAC2 W5500 SPI1, MAC3 W5500 SPI2,
  MAC4/5 USB Ethernet #1/#2, MAC6–8 Reserved. Интерфейсы не сдвигают номера.
- Формат EEPROM не изменён: mac_count 0x17 = 8, MAC1 0x38, шаг 6 байт,
  CRC32 по 0x00..0x67 в 0x68..0x6b. Запись идентичных целиком bytes пропускается.
- `BoardService.mac_plan/apply_mac_plan`: общий preview с OTP/source,

## v20: EEPROM Format v3

- Пользователь передал спецификацию v3: 126 байт, CRC32 `0x7A..0x7D`
  по `0x00..0x79`, proc_id_type `0x68`, proc_id_len `0x69`, ID16 `0x6A..0x79`.
  Спецификация сохранена в `EEPROM_FORMAT_V3.md`. Формат EEPROM 3 и версия
  программы 20 — отдельные номера.
- Core читает v2/v3, выбирая размер и CRC по версии. v2 не трактуется как v3.
  Новый BoardConfig по умолчанию v3. Чтение v2, применение профиля и генерация
  MAC сохраняют формат; обычная полная запись не меняет формат существующей EEPROM.
- Миграция `eeprom migrate --preview/--yes` отдельная, оставляет NOT BOUND,
  сохраняет данные экземпляра и неизвестные биты маски. Legacy RTC bit 0
  преобразуется в RTC bit 13–15; в v3 bit 0 не включает RTC.
- Processor ID: type0/empty либо type1/валидный RK3308 OTP5, padding нулевой.
  Будущие типы пока отклоняются. JSON содержит hex proc_id и производный len.
  Profiles не содержат serial/date/MAC/proc_id и при загрузке сохраняют их.
- Общие `processor_status/processor_plan/apply_instance_eeprom_plan` используют
  порт OtpSource, без fallback. Состояния NOT BOUND/MATCH/PROCESSOR MISMATCH/
  OTP UNAVAILABLE. Обычная запись не меняет сохранённую привязку.
  Для другого SoC требуется explicit rebind; serial/MAC остаются прежними.
- CLI `processor status`, `processor bind/rebind --preview/--yes`.
  TUI показывает состояние и отдельные пункты просмотра, bind/rebind/migrate,
  новые значения первыми, просмотр → Enter → точное yes.
- При миграции/bind/rebind перед записью проверяется полный исходный образ,
  текущий OTP, создаётся проверенная бинарная копия в eeprom-backups рядом с
  выбранной boards.yaml, после записи — read-back. Совпадение пропускает запись.
- MAC-only поддерживает оба расположения CRC, сохраняет proc_id и прочие поля,
  повторно проверяет текущий OTP перед записью на привязанной плате.
  MAC algorithm/slot numbering/set_native_eth_mac не менялись.
- Пользователь ответил на уточнение: **сохранить независимое включение I2C1**.
  Поэтому v3 НЕ требует bit10 при записи/миграции/привязке/MAC-only и не включает
  шину автоматически. RTC по-прежнему требует I2C1. Физический доступ зависит

- Пользователь согласовал Reset EEPROM и View and write processor ID; пока
  работает одна отладочная плата, миграция не нужна как основной сценарий.
- TUI: отдельные bind/rebind/migrate убраны из меню, заменены двумя пунктами.

- Reset: preview всех текущих полей + предупреждение об удалении всех 256 байт,
  Enter → yes → backup полного образа → повторная stale-проверка → write256zero
  → read-back256. Работает с валидной v2/v3 и некорректной EEPROM; короткий
  образ отклоняется. Уже нулевые байты повторно не пишет.
- После подтверждённого reset TUI сбрасывает RAM draft до defaults v3, включая
  serial/date/MAC/proc_id. Отмена сохраняет draft и EEPROM. Далее задать поля

  ради проверки не обнулять: проверять на временных файлах.

## Согласованные правки меню v20 после reset

Этот раздел заменяет прежнее описание очистки RAM draft при reset выше.

- Reset обнуляет только физическую EEPROM, текущие поля в памяти сохраняются.
  Статус процессора обновляется по EEPROM, не по сохранённому draft proc_id.
- Строка Processor ID показывает текущий OTP + (not in EEPROM)/(in EEPROM)
  или PROCESSOR MISMATCH со старым ID; OTP UNAVAILABLE при ошибке источника.
  Старт с нулевой/FF EEPROM показывает EEPROM empty вместо Bad magic.
- View and write processor ID перенесён в ACTIONS рядом с MAC, без дублирования
  в SERVICE. Для пустых 256 байт zero/FF предлагает полный draft+OTP в v3,
  preview всех полей → Enter → yes → backup → stale-проверка → read-back.
  Для корректной v3 изменяется только proc_id, serial/MAC остаются прежними.
  Повреждённая непустая EEPROM не перезаписывается автоматически этим пунктом.
- Обычный Write EEPROM после reset записывает v3, сохраняя значения draft v2.
  После успешной записи RAM формат обновляется, комментарий сохраняется в памяти.
- CLI processor write --config instance.json задаёт draft для пустой EEPROM;
  без JSON defaults. Подтверждение --yes, --preview ничего не пишет.
- Единый View and write boot config вместо отдельных overlay string/current boot.
  Полные файлы, новый первым, warnings отдельно, Enter → yes → backup/read-back,
  без reboot. Пользовательские overlays не сканировать и user_overlays не менять.
- Вверх на первом пункте → последний, вниз на последнем → первый в обеих ширинах.
- Галочку EEPROM пока не добавляли: обсуждалась как вопрос, не согласованная правка.
