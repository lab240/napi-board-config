# NAPI Board Config v21

Утилита для настройки плат NAPI под Armbian и NapiLinux/U-Boot.
Позволяет читать и записывать EEPROM, выбирать профиль платы, задавать серийный
номер и дату изготовления, генерировать MAC-адреса и формировать строку overlays
для загрузчика. Сейчас поддерживается платформа RK3308 и профиль FCU3308.

Доступны текстовое меню (TUI) и неинтерактивная командная строка (CLI).
Оба интерфейса используют общий Core; Linux и аппаратура вынесены в отдельные
адаптеры. Сервер, web-зависимости и отдельная БД не нужны.

Текущая версия программы — **21.0.0**, формат EEPROM — **v3** (чтение v2
сохранено). История версий: [CHANGELOG.md](CHANGELOG.md).

## Зависимости и запуск

Python 3.9+, PyYAML и модуль curses из Python. Для Debian/Ubuntu/Armbian:

```bash
sudo apt install python3-yaml
./napi-config tui
```

Из каталога проекта меню запускается через `./napi-config tui` или
`python3 -m napi_config tui`. Справка: `./napi-config --help`.
Для установки команды в Python-окружение с pip:

```bash
python3 -m pip install .
napi-config --help
```

Для EEPROM и boot-файлов могут потребоваться права root. Сохранён прежний запуск:
`python3 napi-board-config.py`.

## Команды CLI

В примерах используется установленная команда `napi-config`.

| Команда | Назначение |
| --- | --- |
| `napi-config tui` | Открыть текстовое меню |
| `napi-config eeprom overlays` | Показать доступность EEPROM и стандартные оверлеи для включения |
| `napi-config eeprom enable --overlay eeprom24 --yes` | Добавить выбранный стандартный оверлей и I2C1, без reboot |
| `napi-config eeprom show` | Прочитать EEPROM и проверить формат, CRC и значения |
| `napi-config eeprom preview --config instance.json` | Показать все текущие и предлагаемые поля EEPROM без записи |
| `napi-config eeprom write --config instance.json --yes` | Записать конфигурацию и проверить чтением |
| `napi-config eeprom reset --preview` | Показать полное обнуление EEPROM без записи |
| `napi-config eeprom reset --yes` | Обнулить все 256 байт с резервной копией и read-back |
| `napi-config eeprom migrate --preview` | Показать миграцию EEPROM v2 → v3 без записи |
| `napi-config eeprom migrate --yes` | Мигрировать v2 → v3 с бинарной резервной копией |
| `napi-config processor status` | Сравнить сохранённый ID процессора с текущим OTP |
| `napi-config processor reset --preview` | Показать сброс только привязки процессора |
| `napi-config processor reset --yes` | Очистить processor ID с backup и read-back |
| `napi-config processor write --preview` | Показать текущий и предлагаемый ID процессора |
| `napi-config processor write --yes` | Записать текущий OTP ID, явно подтверждая замену старой привязки |
| `napi-config processor bind --preview` | Показать предлагаемую привязку процессора |
| `napi-config processor bind --yes` | Привязать текущий процессор к EEPROM v3 |
| `napi-config processor rebind --preview` | Показать замену ранее привязанного процессора |
| `napi-config processor rebind --yes` | Явно подтвердить привязку нового процессора |
| `napi-config mac preview --json` | Прочитать OTP и показать текущие/генерируемые MAC без изменений |
| `napi-config mac generate --yes --output instance.json` | Сформировать восемь стабильных MAC из OTP и сохранить JSON |
| `napi-config mac write --config instance.json --yes` | Обновить только MAC, mac_count и CRC в корректной EEPROM |
| `napi-config mac assignments --config instance.json --json` | Показать назначения фиксированных MAC-слотов |
| `napi-config board info` | Показать конфигурацию и данные экземпляра из EEPROM |
| `napi-config overlay list` | Сформировать список overlays по конфигурации EEPROM |
| `napi-config boot show` | Показать текущий boot-файл |
| `napi-config boot preview` | Показать текущие/предлагаемые строки и предупреждения без записи |
| `napi-config boot write --yes` | Обновить строку overlays по EEPROM с backup, без reboot |
| `napi-config hardware detect` | Показать обнаруженные I2C, EEPROM и Device Tree |
| `napi-config --version` | Показать версию |

Параметры указываются после раздела и действия:

- `--json` — машинный вывод для всех команд, кроме TUI.
- `--eeprom PATH` — EEPROM device или бинарный файл; по умолчанию
  `/sys/bus/i2c/devices/1-0050/eeprom`.
- `--otp PATH` — путь к RK3308 NVMEM для processor, mac, eeprom preview/write и TUI;
  по умолчанию `/sys/bus/nvmem/devices/rockchip-otp0/nvmem`. В производстве
  использовать реальный NVMEM; временный файл применяется только для тестов.
- `--settings PATH` — YAML настроек назначения MAC, по умолчанию `settings.yaml`.
- `--db PATH`, `--platforms PATH` — пути к YAML-профилям и определениям платформ.
- `--boot-dir DIR` — каталог boot-файлов; по умолчанию `/boot`.
- `--config instance.json` — источник для board/overlay/mac и boot preview/write.
- `--profile ID REV --yes` — reusable-профиль вместо EEPROM/JSON для этих операций.
- `--yes` — явное подтверждение генерации, применения профиля или записи.

Пример подготовки экземпляра без записи EEPROM:

```bash
./napi-config mac generate --profile 6 1 --yes --output instance.json --json
./napi-config board info --config instance.json
./napi-config boot preview --config instance.json --json
```

Генерация MAC без `--config`/`--profile` сохраняет валидную конфигурацию EEPROM,
если она доступна; иначе использует defaults. С `--config` сохраняет остальные
поля экземпляра. Источник MAC во всех случаях — только OTP, serial не участвует.
`--output` сохраняет instance JSON, пригодный для `eeprom write --config`.
JSON stdout генерации содержит `configuration` и `mac_generation` с OTP ID,
источником, текущими и новыми значениями; не подавать этот отчёт целиком как
instance JSON. Без `--output` ничего не сохраняется.
CLI не задаёт интерактивных вопросов. Результаты идут в stdout, ошибки — в stderr.
Коды завершения: 0 — успех, 1 — ошибка операции, 2 — ошибка аргументов,
130 — прерывание.

## TUI и boot-конфигурация

При запуске меню корректная EEPROM-конфигурация загружается автоматически.
Если EEPROM недоступна или некорректна, используются defaults с причиной в статусе.
Чтение/запись недоступного устройства помечается `disabled`; выбор показывает причину.

`View EEPROM` показывает фактическое содержимое устройства: поля платы, serial,
дату, восемь MAC-слотов, processor ID и результат проверки CRC. Текущие настройки
меню при просмотре сохраняются. Для пустой или повреждённой EEPROM показываются
причина и сырые байты. `Load EEPROM` отдельно заменяет настройки меню прочитанной
конфигурацией после подтверждения.


Boot-файл (`armbianEnv.txt` или `uEnv.txt`) определяется автоматически.
При неоднозначности программа не записывает файл. Текущий `overlay_prefix`
сохраняется: с префиксом формируются короткие имена, без него — полные имена
без `.dtbo`. Существующая `user_overlays=` сохраняется без изменений;
произвольные пользовательские overlays не сопоставляются с интерфейсами платы.

`View and write boot config` объединяет просмотр и запись: показывает полный
предлагаемый файл первым и текущий файл вторым, выделяя изменённые строки.
Новый файл формируется из текущих настроек меню. Отдельный пункт просмотра
старого boot-файла убран.
Предупреждения об отсутствующих стандартных `.dtbo` отображаются отдельно
и не блокируют запись. q/Esc закрывает просмотр; Enter открывает подтверждение
точным `yes`. Запись создаёт backup и не перезагружает устройство.
Стрелка вверх на первом пункте переходит к последнему, вниз на последнем —
к первому, в широком и узком меню.
I2C1 включается отдельно от RTC и EEPROM; RTC требует включённой шины.
При выборе I2C1 и DS1338 формируется `overlays=i2c1 i2c1-ds1338`
(без `overlay_prefix` используются полные имена с префиксом платформы).
Наличие шины не означает наличие EEPROM. Оверлей EEPROM автоматически не добавляется.

`Add EEPROM overlay and reboot` предлагает выбор из найденных стандартных
`.dtbo` с EEPROM/24xx в имени. Это кандидаты: пользователь проверяет модель,
шину и адрес, просматривает предложенные строки и подтверждает запись/reboot
точным `yes`. Если EEPROM уже доступна (в том числе через основной DTB),
дополнительный оверлей не предлагается. Если стандартных кандидатов нет,
выводится инструкция установить и настроить подходящий user overlay вручную.
Каталоги user overlays не сканируются, их файлы и строка `user_overlays` не меняются.
Отсутствие sysfs-устройства означает «недоступна / не настроена», а не доказанное
отсутствие микросхемы.

В CLI имя для `eeprom enable --overlay` берётся из поля `name` команды
`eeprom overlays`; с `overlay_prefix` оно короткое, без префикса — полное.
`--yes` подтверждает выбор и запись, `--reboot` дополнительно разрешает reboot.
Без `--yes` ничего не записывается. Например, `eeprom24` подходит только если
это имя выдала команда поиска и пользователь проверил соответствие оборудованию.
Ранее явно включённый стандартный EEPROM-оверлей сохраняется при обычной
генерации boot-строки, пока I2C1 включён.

## EEPROM v3 и привязка процессора

EEPROM 24C02 имеет 256 байт. Формат v3 занимает 126 байт; область
`0x7E..0xFF` сохраняется при записи. Первые поля и восемь MAC-слотов совпадают
с v2. В `0x68` хранится `proc_id_type`, в `0x69` — `proc_id_len`,
в `0x6A..0x79` — 16 байт ID с нулевым дополнением.
CRC32 покрывает `0x00..0x79` и хранится little endian в `0x7A..0x7D`.
Тип 0 означает отсутствие привязки; тип 1 — пять исходных байт RK3308 OTP.
Полная карта полей — в [EEPROM_FORMAT_V3.md](EEPROM_FORMAT_V3.md).
Нулевой/FF ID, неверная длина, ненулевое дополнение и неподдерживаемый тип
отклоняются. Board serial — отдельный uint32, не зависит от процессора.

Программа читает v2 и v3, выбирая размер и CRC по `format_version`.
Новые экземпляры используют v3. Загрузка v2, профиля или генерация MAC не
мигрирует EEPROM автоматически: для существующей v2 нужен отдельный
`eeprom migrate`. Миграция сохраняет данные экземпляра и оставляет процессор
непривязанным. Старый RTC bit 0 преобразуется в соответствующий RTC bit;
в v3 bit 0 зарезервирован. I2C1 остаётся независимой настройкой:
запись v3 не требует отметки этой шины в interface_mask и не включает её
автоматически. Для доступа к физической EEPROM шина должна работать в Linux;
это проверяется доступностью устройства. EEPROM overlay сама не добавляется.

TUI показывает текущий OTP и состояние привязки: `(not in EEPROM)`,
`PROCESSOR MISMATCH` или `OTP UNAVAILABLE`; при совпадении ID выводится без пометки.
При полной `Write EEPROM`, если привязки ещё нет, Core включает текущий OTP
в предлагаемые значения. Он записывается вместе с конфигурацией после `yes`.
Существующий ID не заменяется молча. После замены SoC используйте
`Reset processor ID` → `Write EEPROM`: сброс удаляет только привязку,
сохраняет serial, дату, MAC и остальные байты, пересчитывает CRC.
Если нужны новые MAC, их генерируют отдельно. I2C1 автоматически не включается.

В широком терминале ACTIONS слева и SERVICE справа. Стрелки влево/вправо
переключают списки, вверх/вниз перемещают выбор; навигация циклическая.
В узком терминале пункты показаны одним столбцом, SERVICE после конфигурации.
ACTIONS: View EEPROM, Load EEPROM, Write EEPROM, Load/Save/Delete board from local DB,
Load DB from GitHub, View and generate MACs, View and write boot config.
SERVICE: Load defaults, Reset EEPROM, Reset processor ID,
Add EEPROM overlay and reboot, Quit.

Миграция/привязка: предпросмотр → Enter → точное `yes` в TUI;
CLI требует `--yes`, а `--preview` только показывает изменения.
Перед записью проверяются исходные байты и текущий OTP; сохраняется полная
бинарная копия EEPROM в `eeprom-backups/` рядом с выбранной `boards.yaml`.
Ошибка создания копии блокирует запись. После записи выполняется read-back.
Обратной автоматической миграции v3 → v2 нет; старая v19 не читает v3.

Для пустой EEPROM задайте значения и выберите `Write EEPROM`: текущий OTP
включается в preview. `Reset EEPROM` нужен для намеренного полного обнуления
содержимого, а не перед каждой записью.
Сброс сначала показывает текущие данные и предупреждение об удалении ВСЕХ
256 байт, включая serial, дату, MAC, привязку и резерв. Enter открывает
отдельное подтверждение точным `yes`. Перед записью сохраняется полный
бинарный backup, после — read-back. Текущие настройки в памяти сохраняются,
включая serial, дату и MAC; сброс очищает только EEPROM. Отказ на любом этапе
сохраняет и EEPROM, и текущий черновик. Полная запись в пустую EEPROM использует
v3, даже если черновик был загружен из v2; новые и старые значения показаны заранее.
Пустая EEPROM не содержит корректного заголовка/CRC и требует полной записи;
сброс работает также с некорректной EEPROM. Уже нулевая EEPROM повторно не пишется.

ID процессора читается из OTP, а не генерируется. При `PROCESSOR MISMATCH`
`Reset processor ID` очищает старую привязку через `yes`, затем
`Write EEPROM` предлагает текущий OTP вместе с конфигурацией. Старые CLI
`processor write/bind/rebind` также доступны с явным подтверждением. Для привязки существующей v2
сначала нужна явная миграция в v3 или полная переинициализация. Для CLI `processor write --config instance.json` задаёт поля
инициализации пустой EEPROM; без config используются defaults. При наличии
корректной v3 изменяется только ID из текущего OTP, прочие поля JSON не применяются.
CLI bind/rebind/migrate
сохранены для совместимости, но миграция не нужна для сценария полного сброса.

## MAC из RK3308 OTP

NVMEM открывается только для чтения. `fcntl.flock` берёт exclusive advisory lock
с таймаутом 2 секунды; ID — ровно 5 бинарных байт с offset 20. Offset 8 не
используется. Нет файла/доступа/lock, короткое чтение, ID из нулей или FF — ошибка
`MAC generation failed: invalid or unavailable RK3308 OTP ID`, без fallback.

`SHA256(b"NAPI-MAC-v1\x00" + otp)`: первые пять байт дают основу,
младшие три бита пятого байта обнуляются. Первый октет MAC всегда `02`,
последние три бита последнего октета — номер слота 0..7. Случайность, время,
serial и официальный IEEE-блок CominTech не используются.
Один OTP даёт один набор. 37 бит хеша не гарантируют отсутствия коллизий:
для строгой уникальности между серийными платами нужна производственная
проверка дубликатов; отдельная БД в утилиту не добавлена.

| Слот | Назначение |
| --- | --- |
| MAC1 | Native Ethernet |
| MAC2 | W5500 SPI1 |
| MAC3 | W5500 SPI2 |
| MAC4 | USB Ethernet #1 |
| MAC5 | USB Ethernet #2 |
| MAC6–MAC8 | Reserved |

Отсутствующие интерфейсы не сдвигают слоты. Контрольные примеры:
`0235221703` → `02:98:1C:8E:55:E0`…`02:98:1C:8E:55:E7`;
`090b131d04` → `02:9E:E6:97:4D:60`…`02:9E:E6:97:4D:67`.

TUI `View and generate MACs` показывает текущие адреса и OTP; Enter предлагает
генерацию с просмотром источника и текущих/новых MAC.
q/Esc отменяет, Enter открывает подтверждение точным `yes` (по умолчанию отмена).
После подтверждения генерации MAC меняются в памяти и сразу предлагается
отдельная запись только MAC в EEPROM, с текущими/новыми адресами и ещё одним
`yes`. Отказ сохраняет адреса в памяти. Обновляются MAC (`0x38..0x67`),
при необходимости mac_count (`0x17`) и CRC (v2: `0x68..0x6B`, v3: `0x7A..0x7D`); прочие байты,
включая serial, дату, имя, конфигурацию интерфейсов и резервные биты, сохраняются.
CRC записывается последним, результат проверяется чтением. При совпадении
MAC записи нет. Если EEPROM пустая/некорректная, MAC-only запись отклоняется:
её сначала нужно инициализировать полной конфигурацией.

`Write EEPROM` остаётся полной записью. Просмотр показывает все текущие и
предлагаемые поля текущего формата: платформу, product ID/revision, имя, serial, дату,
маску/интерфейсы, RTC, mac_count, все MAC, привязку процессора в v3 и CRC. Затем требуется `yes`.
В TUI при ширине от 80 символов поля показаны рядом: сначала Proposed EEPROM,
затем Current EEPROM. Изменения отмечены `*` и выделены цветом (или жирным
в терминале без цвета). Длинные значения переносятся внутри столбца.
При меньшей ширине — новые, затем старые значения последовательно с прокруткой.
MAC-only просмотр также сравнивает mac_count и CRC. Подтверждение `yes`
открывается только после Enter в просмотре; q/Esc отменяет.
Comment и строки загрузчика не входят в EEPROM. Совпадающая целиком
EEPROM-конфигурация повторно не записывается. CLI требует `--yes`; для просмотра полной предлагаемой конфигурации
служит `eeprom preview --config instance.json`, для генерации MAC — `mac preview`. После генерации записываются все 8 слотов и штатный CRC32.

В `settings.yaml` параметр `set_native_eth_mac: false` по умолчанию исключает
MAC1 из результата `mac assignments`. При `true` Native Ethernet получает
назначение MAC1. Адрес по-прежнему генерируется и хранится в обоих случаях;
остальные слоты не меняются. Параметр относится к настройкам приложения,
не занимает EEPROM bits и не меняет формат. Команда возвращает назначения
для потребителя; программирования сетевых интерфейсов Linux в проекте пока нет.

## Данные и проверка

`boards.yaml` хранит reusable-профили, `platforms.yaml` — ID платформ, mappings
и конфликты интерфейсов. Serial number, manufacturing date и MAC относятся
к экземпляру: сохраняются в EEPROM/instance JSON и исключены из профилей.
То же относится к `proc_id_type`, `proc_id_len` и `proc_id`.
EEPROM использует формат v3 с CRC32 и восемью MAC-слотами; v2 также читается.
Runtime-потребитель берёт сохранённые MAC из EEPROM и не генерирует их заново
из proc_id. Утилита пока только показывает назначения сетевых MAC.
Загрузка профиля сохраняет данные экземпляра.

```bash
python3 -B -m unittest discover -s tests -v
```

Тесты работают на временных файлах и подставных адаптерах.
