# Архитектура v20

Проект работает одним процессом. TUI, CLI и будущие интерфейсы используют
`core.service.BoardService`. Сервис не хранит текущую конфигурацию пользователя:
операции получают `BoardConfig` и возвращают новую конфигурацию либо результат.
TUI хранит свой черновик, CLI выбирает источник по аргументам.

## Зависимости

```text
TUI / CLI / будущий REST -> BoardService -> модели и правила Core
                                  |
                                  v
                          Protocol из core.ports
                                  ^
                                  |
                         Hardware / Storage

bootstrap создаёт и соединяет реализации
```

Core импортирует только стандартную библиотеку и свои модули.
`core.models` сохраняет существующую модель BoardConfig и EEPROM bit assignments;
instance-поля пока остаются в ней для совместимости. `core.profiles` задаёт отдельное
представление reusable-профиля, исключающее serial/date/MACs/proc_id.
`core.codec` содержит EEPROM formats v2/v3, CRC, даты и вычисление overlays.
`core.configuration` содержит полную проверку, преобразование instance JSON
и изменение конфигурации без частично применённых значений.
`core.mac` содержит чистую OTP→SHA256 генерацию, неизменную семантику слотов
и MacPolicy (`set_native_eth_mac=false`). LinuxOtp читает NVMEM offset 20/length 5
под exclusive flock с таймаутом 2 секунды через порт OtpSource.
BoardService создаёт/применяет MAC-preview для обоих интерфейсов.
Отдельный MAC-only план читает фактическую EEPROM, сохраняет остальные байты,
обновляет восемь MAC/mac_count/CRC и проверяет исходное содержимое перед записью.
Core определяет диапазоны, Hardware.write_ranges выполняет запись (CRC последним)
и общий сервис проверяет read-back. Пустая/невалидная EEPROM требует полной
инициализации. Полная запись показывает все поля текущего формата. Core отдаёт структурированные
поля/различия для сравнения EEPROM; TUI выбирает столбцы или последовательный
просмотр по ширине терминала и выделяет изменённые значения.
После применения генерации TUI предлагает отдельную MAC-only запись с новым yes.
Настройки назначения MAC загружает Storage, валидирует Core, связывает Bootstrap.
Core сравнивает сохранённый proc_id с OtpSource и возвращает состояние привязки.
Миграция v2 → v3, привязка и перепривязка имеют отдельные планы и подтверждения.
Они сохраняют serial/MACs и проверяют исходный образ EEPROM перед применением.
CRC/размер выбираются по версии. Бинарную резервную копию перед изменением
привязки/формата сохраняет Storage через порт ConfigurationFiles; Core проверяет
read-back через EepromDevice. I2C1 независима от версии EEPROM: Core не требует
bit10 при записи, доступность физического устройства проверяется через адаптер.
Reset-план читает полный образ 256 байт, работает и с невалидным заголовком,
проверяет подтверждение/исходные байты, сохраняет backup через Storage,
обнуляет EEPROM и проверяет все 256 байт чтением. Объединённый processor write
план явно показывает замену привязки и сохраняет остальные данные экземпляра.
TUI предлагает reset EEPROM и reset processor ID; полная запись привязывает незаполненный ID;
старые CLI-команды остаются совместимыми. После reset TUI сохраняет свой черновик;
Core не хранит состояние пользовательского черновика. Для пустой EEPROM общий
processor write план использует переданный draft, показывает все поля и после
отдельного подтверждения создаёт v3 с OTP ID, backup и read-back. На валидной v3
он изменяет только привязку. Обычная полная инициализация пустой EEPROM также
выбирает v3. Состояние процессора для меню определяется по фактической EEPROM,
а не draft: сохранённый в памяти ID после reset не считается записанной привязкой.
Boot comparison Core содержит строки полного старого/нового файла, а warnings
остаются отдельным полем плана; TUI показывает new/current и выделяет изменения.
`core.boot` рассчитывает новый текст boot-файла без файловых операций, разбирает текущий
overlay_prefix и разрешает имена по переданному каталогу существующих файлов.
Обнаружение активного env и поиск файлов overlays выполняет Hardware; Core
проверяет доступность операций одинаково для TUI и CLI.

`BoardService` выполняет общие сценарии: чтение/запись EEPROM,
генерацию MAC, применение/сохранение профилей, preview/apply boot-конфигурации.
Он вызывает внешние операции через переданные адаптеры из `core.ports`.
Boot-план содержит текущую/предлагаемую строку, исходное и новое содержимое,
а также предупреждения об отсутствующих стандартных overlay-файлах.
Произвольные user_overlays сохраняются без сопоставления и проверки файлов;
Сервис EEPROM предлагает только существующие стандартные оверлеи-кандидаты
с подтверждением модели, шины и адреса пользователем. Hardware не сканирует
user overlays. I2C1 независим от EEPROM и RTC; RTC требует включённой шины.
При старте TUI общий сервис читает и проверяет EEPROM либо возвращает defaults
с причиной ошибки.
Перед записью требуется подтверждение; перед применением проверяется,
что исходный файл не изменился. Это не блокировка для конкурентных записей.

Hardware отвечает за I2C/sysfs/Device Tree observations, EEPROM I/O,
запись boot-файлов, backups, sync и явно запрошенный reboot.
Наличие sysfs-узла не считается проверкой исправности оборудования.
Storage отвечает за YAML/JSON, backup/замену файлов и HTTP-загрузку профилей
через стандартный urllib. Разбор YAML-ошибок преобразуется в ValueError.

TUI отвечает за curses, ввод, подтверждения и представление результата.
CLI отвечает за argparse, stdout/stderr, JSON и коды завершения.
Оба не открывают EEPROM/boot/profile-файлы и не реализуют бизнес-правила.
Bootstrap — единственное место выбора Linux/file-реализаций.

## Подтверждения и тестирование

Сервис требует `confirmed=True` для операций изменения. TUI передаёт его
после точного `yes`; CLI — при `--yes`. Это контракт интерфейса, а не механизм
аутентификации. Генерация меняет только возвращаемую конфигурацию; запись EEPROM
выполняется отдельной операцией. Boot apply и reboot также раздельные операции.

Общий Core тестируется без Linux и curses. Тесты операций используют подставные
адаптеры, тесты CLI — временные конфигурации и EEPROM-файлы.
Для будущего REST достаточно создать новый интерфейс с тем же сервисом;
web-зависимости в текущий проект не добавлены. Конкурентные аппаратные записи
потребуют отдельно определённой политики доступа при появлении такого интерфейса.

Полная запись v3 без привязки получает ID через OtpSource в Core и включает его
в preview. Существующая привязка сохраняется и проверяется на совпадение с SoC.
Reset processor ID имеет отдельный Core-план: исходный образ, backup, изменение
только 18 байт привязки и CRC, read-back. TUI/CLI используют один этот план.
